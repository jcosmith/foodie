Foodie: Architecture Design (v3)

Architecture of a multilingual, offline, privacy-first Flutter app for household inventory · Version 3 · 3 October 2026 · food first, household supplies as optional basics now and in full later · one bottom-navigation tab per storage domain (Freezer, Fridge, Pantry, Household), plus Lists and More · widens the scope from the freezer to the whole household (section 10.7) and designs two optional modules: pantry management with best-before dates and shelf lives down to a single day (10.8), household supplies for non-food articles (10.9), and an optional receipt scanner with on-device text recognition and a searchable receipt archive (10.10). Version 2 added freezer layout editing, the Config tab and interactive statistics.

1. Summary

Mission. Foodie helps a private household know what it has at home, what to use first and what to buy. It started with the freezer; the goal is every place a household keeps things it regularly stocks up on: freezer, fridge, pantry, kitchen cupboards and household supplies such as cleaning products or toiletries. Three principles hold for all of it: no data ever leaves the app, the code is modular and readable Flutter for phones, and the UI is clean, simple and self-explanatory.

Built versus planned. Release 0.1.1 implemented everything below for freezers. The code since then (not yet released) is Foodie: storage domains with a tab each (10.7), fridge and pantry (10.8), household basics (10.9) and receipt scanning (10.10) are built, and names in code are neutral (StoragePlace, storedOn). Only the full household supplies module (10.9) is still planned. Where this document says "today" or "planned" about those parts, it describes the state before they were built.
Priorities. Food comes first: the freezer, then the fridge and pantry, then receipt scanning, until all of it is set up for regular use. Household supplies (cleaning, bathroom, garden and more) get their bare bones early, off by default so the user can switch them on, and their full feature set afterwards. Every design decision for the food features must keep that expansion open; section 10.7 lists the rules that make sure it does.

The app is built as a Dart pub workspace of small packages: one thin app shell that composes everything, eight core packages that provide shared infrastructure, and eight feature packages that each own one user-facing capability. Every feature follows the same four-layer clean architecture (presentation, application, domain, data) and plugs into the shell through a single FeatureModule contract, which is what makes new features cheap to add.

All data lives in one encrypted SQLite database on the device (Drift + SQLCipher). An append-only inventory movement log records every addition, consumption, discard and move; statistics, restock suggestions and habit analysis are all derived from that log. Features coordinate through an in-process domain event bus, but events are only triggers: the database is always the source of truth, so a lost event never corrupts state.

Three user-facing capabilities are planned in from the start (section 10): partial removal (use 200 g of a 1 kg bag) is part of the core inventory model; item pictures and optional barcode scanning are separate feature packages that plug into the inventory without the inventory depending on them.

Version 2 adds three more: a freezer layout editor (add, rename, reorder and remove drawers) in its own package, a Config tab that holds language selection and every other setting, and a much richer statistics module built around one shared filter that every chart reads and every chart can change (cross-filtering).

Recommended stack: Flutter (stable) · Riverpod for state and dependency injection · go_router for navigation · Drift on SQLCipher for storage · flutter_local_notifications for reminders · fl_chart for charts · Flutter's gen-l10n (ARB files) with intl for localization.
Three findings changed the plan while checking feasibility:
  1. Android Auto Backup and iCloud device backup would copy the database off the device by default. The app must opt out explicitly (section 11).
  2. iOS keeps at most 64 pending local notifications, and Android 14 denies exact alarms by default. Reminders are therefore a rolling daily digest, not one notification per item (section 12).
  3. Drift's DAOs are bound to the concrete database class, which makes splitting the schema across feature packages fragile. The schema lives centrally in core_database, organised by feature folder (decision D4).

Non-negotiable constraints

Data never leaves the app

No network code, no analytics, no crash reporting, no cloud sync, no OS backup of the database. Data only leaves when the user explicitly exports a file.

Modular and clean

Dependencies point inward. Domain code is pure Dart with no Flutter or database imports. Package boundaries are enforced by pubspec dependencies, not by convention.

English, descriptive names

recommendedMaximumStorageDuration rather than maxDur. Enforced through code review and a lint baseline.

Offline and fast

Everything works without connectivity. Inventory sizes are small (hundreds to a few thousand batches), so plain SQL aggregates are fast enough.

3. Technology choices, questioned

Each decision lists the alternatives considered and the reason it could turn out wrong. Click a decision to expand it.

D1 · State management and dependency injection: RiverpodFeasible
Choice

Riverpod providers for both dependency injection (repositories, use cases, services) and UI state (async notifiers per screen).

Alternatives
  • Bloc: very explicit event/state flow, more boilerplate per screen.
  • get_it + ChangeNotifier: simple, but service locator lookups hide dependencies and are harder to override in tests.
Why

One mechanism for DI and state; compile-time-safe overrides make every layer testable (swap the clock, the database, the notification scheduler). Providers are scoped per feature package and wired by the module, so features stay decoupled.

Risk

Riverpod has had API churn between majors. Mitigation: providers only appear in the application and presentation layers; the domain layer never imports Riverpod, so a future switch touches the outer layers only.

D2 · Local storage: Drift on SQLite (with SQLCipher)Feasible
Choice

Drift as a typed SQL layer over SQLite, encrypted with SQLCipher through sqlcipher_flutter_libs.

Alternatives
  • Isar / Hive: fast NoSQL stores, but the original author stopped maintaining them in 2024; community forks exist but carry long-term risk. Aggregations for statistics would be hand-written in Dart.
  • sqflite: raw SQL, no type safety, no generated migrations tooling.
  • ObjectBox: fast, but proprietary core and weaker ad-hoc aggregation.
Why

The data is relational (freezers, compartments, products, batches, movements) and statistics need GROUP BY, date bucketing and joins. Drift offers reactive queries (streams that update the UI), transactions, schema snapshots and migration tests.

Risk

Code generation (build_runner) adds build time. SQLCipher adds roughly 1 to 2 MB to the binary. Both acceptable.

D3 · Modularity: Dart pub workspace with one package per moduleFeasible, with cost
Choice

A pub workspace (supported since Dart 3.6) containing the app plus core and feature packages. A package may only import what its pubspec.yaml declares, so illegal dependencies fail at compile time.

Alternatives
  • Single package with feature folders: least ceremony, but boundaries are only conventions; they erode quietly. Would need a custom lint to enforce.
  • Separate repositories: far too heavy for one app.
Why

Extensibility is an explicit goal. Hard boundaries keep features independently testable, give each package its own localization files, and make a feature removable by deleting one package and one registry line.

Risk and honest cost

Twenty packages is real overhead for a small team: more pubspecs, more barrel files, slower first setup. Mitigation: a package template script, and melos (or plain workspace scripts) to run analyze, test and codegen across all packages. If the overhead hurts, the fallback is to merge small core packages (for example localization and design system) without touching features.

D4 · One central database schema, organised by featureDeliberate compromise
Choice

All tables, DAOs and migrations live in core_database, in folders named after the owning feature (tables/inventory/, tables/restock/, ...). Feature data layers implement their repositories on top of these DAOs.

Alternatives
  • Each feature owns its tables in its own package: purest modularity, but Drift generates DAO mixins bound to the concrete database class, which would live in the app, creating a dependency cycle. Workarounds exist (raw customSelect, generic accessors) but lose type safety.
  • One database file per feature: breaks cross-feature transactions, joins for statistics, and makes backup a multi-file problem.
Why

Migrations must be numbered in one sequence anyway; one schema gives atomic transactions across inventory and restock, simple joins for statistics, and a single-file backup.

Risk

Adding a feature with storage touches core_database. That is acceptable because schema changes need a reviewed migration regardless. Rule: a feature package may only use the DAOs in its own folder; the statistics module is the one exception and is read-only.

D5 · Cross-feature communication: in-process domain event busFeasible
Choice

Publishing features define immutable event classes in their public API (for example StockBatchConsumed). Use cases publish events after the database transaction commits. Other features subscribe during module initialisation.

Alternatives
  • Direct calls between features: explicit, but the inventory would have to know about restock, reminders and every future feature.
  • Transactional outbox table: guaranteed delivery, but too heavy for a single-process app.
Why

New features (meal planning, recipes) can react to stock changes without the inventory changing at all.

Risk

Events can be lost if the app is killed between commit and handling, and event-driven flows are harder to follow. Mitigation: events are hints, the database is the truth. Every subscriber is idempotent and recomputes from the database (restock evaluates current stock, the reminder planner replans from scratch), and the same recomputation runs at app start.

D6 · Localization: gen-l10n with ARB files per packageFeasible
Choice

Each package with UI has its own l10n.yaml and ARB files and exposes a LocalizationsDelegate through its module. core_localization holds shared strings (units, common actions, relative ages like "frozen 3 months ago") and formatters.

Why

Official tooling, ICU plurals and genders, compile-time checked keys, works offline. Per-package ARB files mean a feature brings its own translations.

Subtle point: seeded product names

Seeded catalog entries store a catalogKey (for example product.peas) and are displayed translated, unless the user renames them, which stores a customName. Otherwise switching language would leave half the catalog in the old language. Names the user types are user data and are never translated.

Risk

Translators must edit many ARB files. Mitigation: a script that merges and splits ARB files for translation rounds. Right-to-left layout is supported by using directional padding (EdgeInsetsDirectional) from day one.

D7 · Charts: fl_chart behind a thin wrapperFeasible
Choice

A chart kit in core_design_system: fl_chart for line, bar, stacked bar, pie/donut and sparklines; custom painters for the chart types fl_chart does not have (calendar heatmap, freezer map). Every chart widget takes domain-neutral series data, a colour per series and a "show as table" switch.

Alternatives
  • Syncfusion charts: has heatmaps and treemaps, but a commercial licence.
  • Only custom painters: full control, but tooltips, touch handling and animation would all be rebuilt.
  • A web view with a JavaScript chart library: rich, but adds a browser engine to an app that must never touch the network. Rejected.
Why

MIT licence, actively maintained, touch callbacks for every chart type (needed for cross-filtering). The wrapper means statistics code never imports fl_chart directly, so the library can be replaced.

Risk

Two custom painters with hit testing and accessibility labels are roughly 200 to 300 lines each. Acceptable; both are isolated in the chart kit.

D8 · Navigation: go_router with module-contributed routesFeasible
Choice

The shell builds one GoRouter from routes contributed by modules, with a StatefulShellRoute for the bottom navigation (Home, one tab per enabled storage domain, Lists, More, see 10.7; release 0.1.1 had Home, Freezer, Shopping list, Insights, Config). Notification taps deep-link into routes.

Risk

Route path collisions between modules. Mitigation: each module prefixes its paths with its identifier, and the registry asserts uniqueness at start-up in debug builds.

D9 · Reminders: rolling daily digest via local notificationsFeasible, constrained by platforms
Choice

A reminder planner computes which batches cross their storage threshold and schedules one digest notification per day (at a user-chosen time) for the next 14 days, using inexact scheduling. It replans whenever the inventory changes and at every app start.

Alternatives
  • One notification per item: runs into the iOS limit of 64 pending notifications and spams the user.
  • Background task computing reminders daily (workmanager): iOS background execution is not guaranteed and may not run for days.
Risk

A digest scheduled in advance may mention an item that was eaten meanwhile, unless the app was opened. Mitigation: replanning on every inventory change, and wording such as "3 items have been in the freezer for over 6 months" whose tap opens a live list.

D13 · Freezer layout as its own packageFeasible
Choice

feature_storage_layout owns freezers and drawers (moved out of the inventory). Inventory, onboarding and statistics depend on its public API.

Alternatives
  • Keep them in the inventory: fewer packages, but the inventory grows a whole configuration UI and every layout change touches stock code.
  • Free-form tags instead of drawers: flexible, but real freezers have fixed drawers, and fixed drawers make the "drawer" filter and freezer map in statistics meaningful. Tags can come later as an extra.
Why

Layout changes rarely and has its own rules (unique names, archiving instead of deleting). It also makes "fridge", "pantry" and "supplies" storage kinds mostly a change in one package, which is how the household scope is planned (10.7).

Risk

A drawer removed today still appears in last year's statistics. Mitigation: drawers are archived, never deleted, and shown as "Drawer 3 (removed)" in historical views.

D14 · Language: in-app choice, synced with the systemFeasible
Choice

The Config tab offers "System language" plus every supported language, each written in its own language ("Deutsch", "English"). The choice is stored in preferences and applied instantly through a Riverpod locale provider feeding MaterialApp.locale; no restart.

Alternatives
  • Only follow the phone language: simplest, but many people run their phone in English and want household apps in their own language.
  • Only the OS per-app language setting (Android 13+, iOS 13+): hidden deep in system settings, and missing on older Android versions.
Why

Language must be easy to find (the user explicitly wants it in the Config tab). Declaring the supported locales to the OS keeps the system's per-app language screen working too; on Android 13+ a small platform channel calls LocaleManager so both places always show the same choice.

D15 · Statistics: one filter object drives every chartFeasible
Choice

An immutable StatisticsFilter (period, comparison, granularity, measure, categories, products, freezers and drawers, movement kinds) lives in one Riverpod notifier. Every chart's query provider watches it; tapping a chart element returns a modified filter (cross-filtering). Filters can be saved as named views.

Alternatives
  • Filters per chart: simpler code, but users lose track of which chart shows what.
  • Load everything into memory and filter in Dart: fine for a year of data, wasteful after five.
Why

One mental model ("everything on this screen shows the same slice"), one place to reset, and the filter is a pure Dart value that is trivial to test and persist.

Risk

A filter change re-runs around ten aggregate queries. Mitigation: queries run on Drift's background isolate, are debounced by 150 ms, and charts below the fold load lazily.

D10 · Quantities: integers in base unitsFeasible
Choice

A Quantity value object holds an integer amount plus a QuantityUnit. Grams and millilitres are stored as whole numbers; pieces and portions are stored in thousandths, so "half a pizza" is exactly 500.

Alternatives
  • Floating point: 1000 − 200 − 200 − 600 may not be exactly 0, so a batch never reaches "empty".
  • Decimal package: correct, but slower and awkward to store in SQLite.
Why

Partial removal makes subtraction the most common operation. Integers make it exact and make sums in SQL exact too.

Risk

Unit mix-ups when a product's canonical unit changes. Rule: the canonical unit is fixed once a product has stock; changing it requires converting every batch through a dedicated use case.

D11 · Pictures: encrypted files plus a metadata rowFeasible, extra encryption step
Choice

Pictures are stored as files in the app's private Application Support folder, encrypted with AES-GCM. The database holds only a row with the file name, owner, size and dimensions.

Alternatives
  • BLOBs in the database: automatically encrypted by SQLCipher, but the database grows by tens of megabytes, every query page competes with images in the cache, and backups cannot leave pictures out.
  • Plain files: simplest, but they would be the only user data not encrypted at rest.
Why

Keeps the database small and fast, lets backups include or skip pictures, and loads thumbnails lazily.

Risk

Files and rows can get out of sync (file written, app killed before the row is inserted). Mitigation: write the file first, then the row; an orphan sweep at start-up deletes files without a row and rows without a file.

D12 · Barcode scanner: mobile_scanner behind an interfaceFeasible, verify configuration
Choice

mobile_scanner wrapped by a BarcodeDecoder interface. On Android it uses ML Kit with the bundled model (shipped inside the app, works offline); on iOS it uses Apple's on-device Vision framework.

Alternatives
  • flutter_zxing (open-source ZXing-C++): no Google code at all, but weaker on damaged or curved codes on frozen bags.
  • Unbundled ML Kit through Google Play services: smaller app, but downloads the model over the network. Rejected.
Why

Most robust recognition, which matters for crumpled frozen packaging. The release build has no INTERNET permission, so even closed-source code inside the app cannot send anything.

Risk

Plugin defaults change between versions. At implementation time verify that the bundled model variant is configured, and keep the interface so the scanner can be swapped for flutter_zxing.

D16 · Receipt text recognition: on-device OCR behind an interfaceBuilt
Choice

A ReceiptTextRecognizer interface returning text lines with their position on the image. On Android it is implemented with ML Kit text recognition using the bundled Latin model (shipped inside the app, works offline), through google_mlkit_text_recognition; on iOS with the same plugin or Apple's on-device Vision text recognition. Everything after recognition (finding item lines, prices, quantities, the date and the total) is pure Dart in the domain layer.

Alternatives
  • Tesseract (open source, for example through flutter_tesseract_ocr): no Google code, but noticeably weaker on faded thermal paper and curved receipts, and its language data adds 10 to 20 MB.
  • Cloud receipt APIs (Google Document AI, AWS Textract, Veryfi and similar): very accurate and already structured, but every receipt would leave the phone. Rejected.
  • An on-device language model for parsing: flexible, but large, slow on older phones and hard to test. The rule-based parser plus learned mappings is predictable and testable.
Why

Receipt text is short, printed and Latin script, which on-device OCR handles well. Keeping the parser in pure Dart means it is tested with recorded OCR output from real receipts, without a camera. The release build has no INTERNET permission, so the recognizer cannot send anything even if it wanted to.

Risk

Receipt layouts differ by store and country, and thermal paper fades. Mitigation: the user always reviews before anything is added, mappings are learned per store, and unrecognised lines are flagged instead of guessed. At implementation, verify that the bundled model is configured and that the plugin pulls in no network-capable dependency (the allowlist check in CI catches new packages).

4. Layered architecture inside each feature

Every feature package has the same four layers. Arrows show the allowed direction of source-code dependencies. The domain layer depends on nothing; the data layer implements interfaces the domain defines (dependency inversion).

Rule of thumb: if a domain file needs import 'package:flutter/…' or package:drift, it belongs in another layer.

Is four layers too many?

For simple screens (a settings toggle), a use case that only forwards a call is ceremony. The rule is therefore relaxed: a use case is required whenever an action writes data, touches more than one repository, or publishes an event. Pure reads may go from a notifier straight to a repository or query service.

Dependency rules

Ideas this design should not block

  • QR labels for homemade meals: print a label whose QR code holds the batch id, so leftovers can be scanned out like bought goods.

9. Data model

Core entities and their relationships. Quantities are stored in the product's canonical unit (pieces, grams, millilitres or portions), so no unit conversion is needed for thresholds.

Why an append-only movement log

StockBatch.quantityRemaining is the fast current state; InventoryMovement is the history. Both are written in the same transaction by the inventory use cases. Movements are never updated or deleted (a correction is a new movement of kind corrected), so statistics can always be recomputed, and a batch can be archived without losing its history because movements also carry productId.

Questioning it: keeping two representations risks them drifting apart. A debug-only consistency check verifies that the sum of a batch's movement deltas equals its remaining quantity, and the same check runs in repository tests.

Supporting tables

  • preference_entries: typed key-value settings (inside the encrypted database, so they are part of every backup).
  • scheduled_notification_records: which notification ids are currently scheduled, so replanning can cancel precisely.
  • schema_metadata: app version that last migrated the schema, used to validate backups on restore.

10. Features beyond the core

Partial removal, pictures, barcode scanning (added in draft 2), and freezer layout editing, the Config tab and in-depth statistics (added in version 2) are designed so that the foundation does not have to change later. All of them are built. Section 10.7 plans the next step, from the freezer to the whole household. Partial removal is part of the inventory itself. Pictures and barcode scanning are separate packages that the inventory never imports; they plug in through the extension points in section 7.

10.1 Partial removal

Example: a 1 kg bag of spinach, frozen on 3 March. The user takes 200 g. The batch now holds 800 g and is still "frozen on 3 March", so its storage age keeps counting from the original date.

  • Model: StockBatch keeps initialQuantity and quantityRemaining. Each removal appends an InventoryMovement with a negative delta. A batch at zero is marked depleted and hidden, but kept for statistics.
  • Use case: ConsumeStockUseCase(batchId, Quantity) returns a failure if the amount is zero, larger than what is left, or in a different unit. Integer quantities (D10) keep the arithmetic exact.
  • Package sizes: products carry an optional defaultPackageQuantity (1000 g for spinach) that pre-fills the add form.
  • Moving part of a batch to another compartment splits it: a new batch with the same frozenOn and a parentBatchId.
  • Interaction: quick buttons for ¼, ½, ¾ and "all", a slider that snaps to steps that suit the package (1 g or ml for packages under 50, 10 up to 200, 50 above, ½ piece), exact entry, and an undo snackbar. The take sheet starts with the amount usually taken of that product (the average of earlier removals), or about a fifth before the first one. Undo appends a compensating movement, so the log stays append-only.
  • Questioning it: people rarely weigh what they take. The quick fractions accept estimates, and a later "correct remaining amount" action records the difference as a corrected movement instead of forcing precision up front.

10.2 Item pictures

New packages: feature_item_pictures (picture table, capture and gallery screens, clean-up) and core_media_storage (encrypted file store, resizing, thumbnails).

  • What gets a picture: a product (the catalog photo, used everywhere) and optionally a batch (useful for homemade meals and leftovers, where a photo of the box is the best label).
  • Capture: image_picker for the camera or the system photo picker. On Android 13 and later the photo picker needs no storage permission.
  • Processing: longest edge 1600 px, JPEG quality about 80, giving roughly 200 to 400 KB per photo, plus a 256 px thumbnail. Re-encoding removes all EXIF metadata, including the GPS location many phones embed.
  • Storage: encrypted files plus a metadata row (D11). The file key lives in Keychain or Keystore next to the database key.
  • Integration: the module implements ItemVisualProvider; inventory list tiles ask the registry for a visual and fall back to the category icon. The inventory never imports the pictures package.
  • Clean-up: the module listens to batch and product deletion events and removes pictures; the start-up orphan sweep catches anything missed.
  • Backup: the backup archive contains the database snapshot plus the picture files. 200 photos at 300 KB is about 60 MB, so the export screen offers "without pictures".
The file is written before the row. A crash between the two leaves an orphan file, which the start-up sweep removes.

10.3 Barcode scanning (optional)

New package: feature_barcode_scanning. It is off until the user turns it on in the Config tab, and the camera permission is only requested on the first scan.

  • Learning codes: a code is mapped to a product once. An unknown code asks "Which product is this?" with search over existing products or "create new". A product can have several codes (two brands of peas), stored in ProductBarcode. No online product database is ever queried (section 11).
  • Scan to add: opens the add sheet pre-filled with the product, its default package quantity and the compartment used last time.
  • Scan to remove: barcodes identify products, not individual bags, so the app suggests the oldest batch of that product (first in, first out) and opens the partial-removal sheet. With several batches the user can pick another.
  • Unpacking groceries: a continuous mode scans many items in a row into a review list, then adds them all in one transaction.
  • Weighed goods: in-store barcodes for loose meat or cheese embed weight or price (GS1 prefixes 02 and 20 to 29), so every package has a different code. These are recognised and matched on the item part only, and the embedded weight pre-fills the quantity when present.
Scanning reuses the inventory's own use cases, so restock and reminders react exactly as they do to a manual removal.

10.4 Customizing the freezer: drawers and names

New package: feature_storage_layout (D13). Its editor is shown as the "Freezer layout" section of the Config tab.

  • Freezers: add one from a template (upright with 3, 5 or 7 drawers, chest freezer with baskets, fridge freezer compartment) or empty; rename; reorder; archive.
  • Drawers: add, rename inline, reorder by dragging, pick a colour tag and an icon, remove.
  • Default names are translation keys ("Drawer {number}") until the user renames a drawer, which stores a customName. Switching language therefore renames untouched drawers, never the user's own names (the same rule as seeded products).
  • Removing a drawer that holds items asks where its items go ("Move 4 items to Drawer 2"). MoveContentsAndArchiveCompartmentUseCase moves every batch, writes moved movements and archives the drawer in one transaction. An empty drawer is archived directly. Nothing is ever hard-deleted, so past statistics keep their drawer names.
  • Validation: names are 1 to 30 characters and unique within a freezer, ignoring case; a freezer keeps at least one drawer.
  • Events: CompartmentCreated, CompartmentRenamed, CompartmentReordered, CompartmentArchived. The inventory list regroups and the freezer map in statistics redraws.

10.7 From freezer to household (built)

The household scope reuses the existing architecture. No new layer is needed; the work is generalising names, dates and seeded data that were written for freezers, adding two optional feature modules (10.8 and 10.9), and two new contributions to the module contract. Nothing in 10.7 to 10.9 is built yet.

  • Bottom navigation: Home · Freezer · Fridge · Pantry · Household · Lists · More, each domain tab only while it is switched on. A new install has six tabs (Home, Freezer, Fridge, Pantry, Lists, More); with Household on it has seven.

  • More holds Statistics (today's Insights screens, unchanged) and Options (today's Config: tabs, optional features, language, appearance, reminders, backup, about and privacy). Future modules add sections to Options or entries to More, never new tabs.
  • Beyond five tabs: Material recommends three to five destinations. Six or seven stays usable on phones because labels are one short word with an icon, and tab order is fixed so muscle memory holds. A household that switches off what it does not use gets back to five or fewer.
  • Tab icons and colours: every tab uses a colour icon in one consistent style, never a mix of colour and monochrome icons. Each domain also has an accent colour token in the design system (Freezer blue, Fridge teal, Pantry amber, Household green) used for its tab icon and storage-place headers. Colour is never the only cue: each tab keeps its label, and the accents meet contrast requirements in light and dark mode.
  • One screen, every domain tab: the inventory provides one generic stock screen (search, grouping by storage place, use-first sorting) that each domain tab mounts with its own domain. A domain module adds its storage kinds, catalog and labels, not its own list screen.
  • Switching a domain off removes its tab and everything it contributes elsewhere: its items in Home's "Use soon" card, its shopping-list entries and its restock rules pause, and its storage places drop out of pickers. Nothing is deleted, and switching it back on brings the tab and everything in it back as it was. Backups always contain every domain.
  • At least one domain stays on. The last enabled switch is disabled with a short explanation, so the app never has nothing to show.
  • The freezer becomes a domain module like the other two: feature_freezer takes over the freezer storage kinds and templates from storage_layout and the frozen-food catalog from product_catalog. This is a move, not a change in behaviour; storage_layout and product_catalog become domain-neutral.

Keeping household supplies open

Supplies are built after the food features, but nothing built before them may close the door. These rules apply to every food feature from 10.7 onwards, and reviews check them:

  • No food-only core types. Inventory, catalog, restock, reminders and statistics speak of products, stock and use, never of food. Food-specific words live only in ARB strings and in the pantry module.
  • Domains are data. The storage domain is a value carried by storage kinds and categories, not a hard-coded list of two. Adding a domain is a new module plus its contributions and its tab, with no change to the inventory or the shell.
  • Dates are optional. Every date except storedOn may be empty, and an item with no dates is valid and never "overdue". Supplies without expiry must fit without special cases.
  • Waste is a domain property. Statistics decide whether discarding counts as waste from a flag on the domain, not from a list of food categories.
  • Receipts are not food-only. The receipt matcher matches against every product in every enabled domain, and lines it cannot place are flagged, never dropped as "not food". Once supplies exist, the same receipt adds dish soap and milk in one step.
  • Units stay generic. Pieces with a display name ("roll", "tab", "bottle") are planned for supplies and must not be blocked by food-specific unit handling.

What does not change

  • Privacy: both catalogs are seeded offline. Product lookup services (Open Food Facts and similar) stay out of scope, for groceries and household goods alike.
  • Architecture: the same packages, layers, module contract, event bus and single encrypted database. Pantry and supplies are feature packages that the inventory never imports, like pictures and scanning.
  • Simplicity: a household that only wants the freezer switches the pantry off and sees one stock tab, as today. Five bottom-navigation tabs stay the ceiling.

10.8 Fridge and pantry (built, optional, both on by default)

New packages: feature_fridge (the Fridge tab) and feature_pantry (the Pantry tab). Together they cover food kept outside the freezer. Both are thin domain modules: the best-before, opened-on and shelf-life machinery lives in inventory and product_catalog (10.7), so the two only add storage kinds, catalogs and wording, and a household can switch each one on or off on its own. What sets them apart from the freezer is time. Frozen food lasts months; milk lasts days, bread two or three, fresh herbs one. Best-before dates and opened packages matter more than storage age.

  • Storage kinds and templates: Fridge tab: fridge (shelves, door, vegetable drawer), drinks fridge, wine fridge. Pantry tab: pantry (shelves), kitchen cupboard (shelves), cellar, drinks crate. Contributed through storageKindContributions; the layout editor, the move flow and archiving work unchanged.
  • Best-before date: the add sheet shows a "Best before" field for pantry kinds, pre-filled from the product's typical shelf life (bought today + 7 days for yoghurt) and editable with a date picker or quick chips (+1 day, +3 days, +1 week). Barcode "scan to add" opens the same sheet.
  • Short shelf lives: shelf life is entered in days, weeks or months. One day is the minimum (fresh herbs, bakery rolls, fresh fish). The reminder digest is already daily, so an item that goes off tomorrow shows up in tomorrow's digest and on today's "Use soon" card.
  • Opened packages: "Mark as opened" on a batch records openedOn. Products can carry a shelf life after opening (milk 3 days, pesto 5 days, jam 4 weeks); the earliest date wins. Opening is one tap on the batch, never a required step.
  • Use soon: the existing dashboard card and digest show pantry items next to freezer items, ordered by date. Badges read "Use by Thu", "Use today", "Past best before" (best-before is a quality date, so the wording never says "dangerous"). Status uses colour, icon and word, as today.
  • Moving between domains: moving a batch from the fridge to the freezer is the existing move use case. The batch keeps its storedOn date and the freezer's storage duration takes over; the app offers "Frozen today" as the new date because freezing resets the clock for most food.
  • Seeded catalog: fridge: dairy and eggs, fresh fruit and vegetables, meat and fish (fresh), cold cuts, ready meals and leftovers, opened jars and sauces. Pantry: bread and bakery, dry goods (pasta, rice, flour, cereals), tins and jars, spices and condiments, oils and vinegar, baking, breakfast and spreads, snacks, drinks. Each product has a typical shelf life and, where it matters, a shelf life after opening.
  • Restock: unchanged. Staples (pasta, flour, coffee, eggs) are the typical restock rules.
  • Switched off: the Fridge or Pantry tab disappears. Its items leave the "Use soon" card and pickers, and restock rules for its products pause, so they do not fill the shopping list. Nothing is deleted.
  • Fridge, freezer compartment: the freezer compartment of a fridge stays a freezer storage kind, because what matters is the temperature, not the appliance.
Data model: stock_batches.opened_on (nullable date), products.shelf_life_after_opening_days and categories.shelf_life_after_opening_days (nullable), categories.storage_domain. best_before_on already exists. One migration, shared with the renames in 10.7.

10.9 Household supplies (optional, off by default; basics early, full later)

New package: feature_household_supplies, shown as the "Household" tab. It covers non-food articles a household uses up and buys again. It is built in two steps. The bare bones come early, right after the pantry, so a household can switch it on: the tab, its storage kinds and templates, a small seeded catalog (cleaning, laundry, bathroom, kitchen paper), and the existing quantities, restock rules and shopping list, which already work for any product. The full feature set below follows once the food features are in regular use. For these the question is rarely "what should I use first?" and almost always "do we still have some, and where?", so restock and the shopping list do most of the work.

  • Storage kinds and templates: cleaning cupboard, bathroom cabinet, laundry room, garden shed, garage, storage room, first-aid box. Compartments are shelves or boxes, named by the user as everywhere else.
  • Seeded catalog:
    • Cleaning: dish soap, dishwasher tabs, all-purpose cleaner, glass cleaner, descaler, sponges and cloths, bin bags.
    • Laundry: detergent, softener, stain remover.
    • Bathroom and personal care: toilet paper, hand soap, toothpaste, toothbrushes, shampoo, shower gel, deodorant, razor blades, cotton pads, sanitary products.
    • Kitchen paper and wrap: kitchen roll, tissues, aluminium foil, cling film, baking paper, freezer bags (handy next to the freezer).
    • Garden: potting soil, fertiliser, seeds, plant food, slug pellets, bird food.
    • Pets: dry food, wet food, litter.
    • First aid and medicine: plasters, disinfectant, painkillers, sun cream (these carry an expiry date).
    • Technical: batteries (AA, AAA, 9 V), light bulbs, fuses.
    • Baby: nappies, wipes. Office: printer paper, ink.
  • Units: most supplies are counted in pieces (rolls, tabs, bottles). The existing piece unit covers them; a product can name its piece ("roll", "tab") for display. Partial removal still works for "half a bottle".
  • Dates: no storage age and no reminder by default. Products that expire (medicine, sun cream, seeds, batteries) use the same best-before field as the pantry, labelled "Expires", and appear in the "Use soon" card.
  • Restock first: adding a supply product offers to set a minimum right away ("Keep at least 2 packs of toilet paper"), because that is why people track supplies. The shopping list groups entries by domain so food and supplies can be bought in different shops.
  • Statistics: supplies appear in usage and "runs out in" charts, never in waste or "eaten" figures. The domain filter separates them from food.
  • Bare bones versus later: everything above except the storage kinds, the first four catalog groups and plain restock rules is part of the later step: the full catalog, named pieces, expiry dates, the restock-first add flow and the statistics views.
  • Out of scope: things a household keeps but does not use up (tools, furniture, electronics). That is an inventory of possessions, not of stock, and would need warranties, values and locations of single objects.

10.10 Receipt scanning (built, optional, off by default)

New package: feature_receipt_scanning. After shopping, the user photographs the receipt. Text recognition on the phone reads it, the app suggests the purchases to add to the household, and the user confirms them in one step. Every receipt is archived, and its text is searchable. Off by default like barcode scanning, because it uses the camera; it is one switch in Config → Optional features.

Receipt archive and search

  • Where: the "Receipts" segment of the Lists tab, next to the shopping list, and the end of every receipt scan. No tab of its own.
  • Search: full-text search over the recognised text and the parsed item names, with filters for store, period and amount. "olive oil" finds every receipt that mentions it; results highlight the matching line and open the receipt image at that line.
  • Index: an SQLite FTS5 table inside the encrypted database, updated in the same transaction as the receipt row. It is part of every backup and rebuilt on restore if missing.
  • Correcting text: the user can correct a misread line; the correction is what gets indexed and learned, and the original OCR output is kept for reference.
  • Retention: receipts are kept until the user deletes them. An option keeps only the text after a chosen time (for example 12 months) and deletes the images, which take most of the space. Backups can leave receipt images out, like item pictures.
  • Prices: parsed lines keep their prices as part of the receipt. Stock batches do not get a price field; spending statistics stay an open question (section 16), and the receipt archive is what would feed them.
Data model: receipts (id, store name, purchased on, total, currency, page count, created at), receipt_pages (receipt id, page number, picture reference, raw OCR text), receipt_lines (receipt id, position, recognised text, corrected text, quantity, unit price, line total, status matched/suggested/unrecognised/ignored, product id, stock batch id), receipt_text_mappings (normalised store, normalised line text, product id or "ignore") and the FTS5 table receipt_search_index.
Privacy on receipts: receipts can carry the last digits of a payment card, a loyalty number and the store's address. The text parser masks card and loyalty numbers before the text is stored or indexed. Images keep everything, so they are encrypted like all pictures and never shown in the search results list, only when the user opens a receipt.

Consequence: losing the phone means losing the data, unless the user exports a backup. The data portability module is therefore part of the first release, not a later nice-to-have, and the app reminds the user every few months to export a backup.

The backup is an archive containing a consistent database snapshot (taken with SQLite's VACUUM INTO) and a manifest with schema version and app version. It is encrypted with a password unless the user switches the protection off when saving; the dialog then warns that anyone who gets the file can read the data, the file is a plain SQLite database, and restoring it asks for no password. The user chooses where it goes through the system save or share dialog; the app itself never sends it anywhere. Restoring an older schema runs the normal migrations; restoring a newer schema is refused with a clear message.

Encrypting picture filesAES-GCM on a 300 KB file takes milliseconds with native crypto (for example cryptography_flutter).Fine decrypt thumbnails lazily and cache them in memory.
Receipt OCR offlineML Kit text recognition has a bundled Latin model for Android; iOS has on-device Vision text recognition. Both run without network.Fine verified: only the bundled Latin model is included; the other scripts are left out and the release build tells R8 so (D16).
Parsing any store's receiptLayouts, abbreviations and quantity formats differ by store and country; thermal paper fades.Changed rule-based parser plus per-store learned mappings, user review before adding, unrecognised lines flagged instead of guessed.
Full-text search in the encrypted databaseSearching receipts needs an index; SQLite's FTS5 works inside SQLCipher because encryption is below the page level.Fine verified: the receipt search index is an FTS5 table in the SQLCipher database.
Receipt image sizeGreyscale JPEG at about 1600 px height per page is roughly 150 to 300 KB; a weekly shop for a year is 15 to 30 MB.Fine with "keep text only after N months" and "export without pictures".
Heatmap and freezer map chartsfl_chart has line, bar, pie, scatter and radar charts, but no calendar heatmap or treemap-style map.Changed two custom painters in the chart kit (D7).
About ten charts re-querying on every filter changeEach is one indexed aggregate over at most tens of thousands of movements, so milliseconds each on Drift's background isolate.Fine debounce 150 ms; lazy-load charts below the fold.
Summing amounts across productsGrams, millilitres and pieces cannot be added up meaningfully.Changed a measure selector; never mix units in one chart.
Language picker in the appMaterialApp.locale switches instantly. Android 13+ and iOS also have per-app language screens in system settings.Fine declare supported locales to the OS; a platform channel keeps Android 13+ in sync (D14).
Removing a drawer that holds itemsBatches and past movements reference the drawer.Changed move contents, then archive; never hard-delete (D13).
Five bottom-navigation tabsMaterial guidelines allow 3 to 5 destinations.Changed for storage domains: Home, up to four domain tabs, Lists and More, so six by default and seven at most; accepted for one-word labels with icons, and fewer when domains are switched off. With seven tabs on a narrow phone the labels shrink slightly to stay on one line.
Recommended storage durationsValues like "beef 6 to 12 months" vary by source and are guidance, not safety guarantees.Fine seeded defaults, editable, labelled as recommendations.

16. Open questions for the product owner

  1. Target platforms: this plan assumes Android and iOS. Desktop or web would change the encryption and notification choices.
  2. Initial languages: the plan assumes English and German first; any right-to-left language planned early?
  3. OS backups: the plan excludes the database from Google Drive and iCloud backups. Some users might prefer the convenience; should it become an opt-in setting?
  4. Prices: the receipt archive keeps the price of every receipt line. Should that feed "money spent" or "money wasted" statistics, or should prices stay inside the archive?
  5. Household sharing: is shared stock between the phones of one household a future goal? It shapes whether ids should be globally unique now (the plan uses UUIDs anyway, so this stays open cheaply).
  6. App name: the repository and project are called Foodie, the installed app is still called Freezer. Is Foodie the name for the household app?
